# GoBoot

把项目约束转成可追溯的技术决策，再按用户确认的方案初始化 Go + Vue 工程。不要把固定模板冒充架构设计，也不要在用户只要求方案时创建项目文件。

## 工作流程

### 1. 确认目标和深度

先确认本次结果用于技术讨论、正式立项还是直接初始化项目。若用户没有指定问诊深度，使用结构化提问让用户选择：

- `快速`：6 题，只给出核心栈和目录方向。
- `标准（推荐）`：13 题，覆盖产品、团队、规模、前端、后端、数据、部署和验收。
- `深入`：19 题，补充合规、集成、预算、发布和运维约束。

最终题量由用户决定。用户已经提供的信息不得重复询问；可以将已知答案预填或从临时配置中删除对应问题。

### 2. 使用本地决策表

问题超过 4 道时，使用本技能的本地表单，不逐题刷屏：

1. 使用 `mktemp -d` 建立本次临时目录。
2. 运行 `python3 <技能目录>/scripts/generate_form.py <技能目录>/assets/intake.json --level <quick|standard|deep> --output <临时目录>/goboot.html`。
3. 在 macOS 使用 `open <临时目录>/goboot.html` 自动打开；其他系统使用对应本地打开命令。
4. 告知用户填写后点击“一键复制 JSON”，将结果粘贴回对话。
5. 解析返回 JSON；`null` 表示未知或跳过，不得擅自补成确定事实。

表单和答案不得包含密码、Token、生产 DSN 或其他密钥。原始答案默认不归档；只有用户明确要求时才保存。

若用户已经给出了足够约束，直接进入决策，不强制打开表单。

### 3. 形成决策

读取 [技术决策指南](references/decision-guide.md)，逐项给出：

- 推荐选择及与当前约束的对应关系。
- 至少一个现实备选及不选它的原因。
- 未来需要重新评估的量化触发条件。
- 明确不引入的组件，避免把“可能有用”变成当前依赖。

版本号必须在执行时从官方发布源或包管理器核对，不使用技能文件中的静态版本号。

默认起点是单仓库、模块化单体、REST、PostgreSQL。默认不是结论；只要问卷证据触发其他方案，就覆盖默认值并说明代价。

### 4. 先确认再初始化

先展示简洁决策表、目录树、依赖方向和主要风险。存在多个合理方案时，使用结构化提问确认最多 3 个关键分歧。

除非用户已经明确要求直接创建，否则在技术方案确认前不生成业务项目。确认只授权当前目标目录内的初始化，不扩大为部署、发布、云资源创建或外部消息发送。

### 5. 初始化项目

用户确认需要落地时，读取 [脚手架与验收基线](references/scaffold-baseline.md)：

- 先检查目标目录、Git 状态和项目级指令；非空目录不得覆盖已有文件。
- 优先使用 Go、Vue 和所选库的官方初始化工具。
- 只创建当前启动链路实际需要的包；不生成空接口、空 Repository 或“以后可能用”的中间件。
- 把最终技术决策写入根目录 `AGENTS.md` 和 `docs/architecture/0001-foundation.md`，不要保存原始问卷。
- 用户只要结构时，不安装依赖；用户要求可运行基础项目时才安装并执行对应检查。
- 不自动启动长期运行的开发服务，不自动提交或推送，除非用户明确要求。

### 6. 验证与交付

验证范围随实际生成内容调整：

- Go：格式、测试、竞态测试（存在并发逻辑时）、`go vet`、构建和包依赖环。
- Vue：安装锁文件、类型检查、Lint、测试和生产构建；没有配置的命令不得伪造执行结果。
- 配置：示例环境文件不含真实密钥，必填配置能在启动边界失败。
- 架构：前端不能直接接触数据库或后端密钥；业务层不依赖传输层；跨模块依赖与决策文档一致。

最终汇报必须区分已完成、验证结果、明确延期和重新评估触发条件。

## 决策纪律

- 团队能力和业务约束优先于流行度。
- 小团队优先模块化单体；没有独立发布和独立扩缩容需求时不拆微服务。
- 优先平台能力、标准库和已选依赖；没有真实需求时不加 Redis、Kafka、Kubernetes、GraphQL 或多数据库。
- 安全边界、输入校验、事务一致性、可恢复性和可观测性不能以“简化”为由省略。
- 原型使用退出条件；生产项目使用 API 延迟、前端体验和可用性等可测指标。
- 架构图只表达真实依赖和数据流，不画尚未实现的未来系统。
