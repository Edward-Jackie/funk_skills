# Go + Vue 技术决策指南

这份指南只提供决策边界，不替代项目问卷。每次输出都要把“当前证据、推荐、备选、重新评估条件”放在同一张表里。

## 默认基线

适用于单团队、客户产品或内部系统、关系数据为主、没有已验证超大流量的项目：

| 层次 | 默认选择 | 只有出现这些证据才切换 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Vue Router | 公开页面需要 SSR/SEO 时评估 Nuxt；不要因为“以后可能 SEO”提前换 |
| 客户端状态 | 组件状态优先；跨页面状态再用 Pinia | 服务端缓存、分页和失效复杂时加入 Vue Query 类库 |
| 后端 | Go + Gin 的模块化单体 | 只有极小且无中间件需求的服务才退回 `net/http`；多团队独立发布才拆服务 |
| 配置 | Viper + 环境变量覆盖 | 配置极少且只有单一进程时可用标准库，不能为热更新提前引入复杂度 |
| 数据库 | PostgreSQL | 文档主导且关系约束很少时才评估文档库；高写入前先做容量验证 |
| 持久化 | GORM 处理普通 CRUD，事务内允许 Raw SQL | 查询形状复杂、SQL 性能是核心指标、希望编译期查询校验时评估 sqlc |
| 迁移 | Goose 版本化迁移 | 不使用生产 `AutoMigrate` |
| API | REST JSON + 统一错误包络 | 强类型内部服务网格评估 gRPC；多端聚合且字段需求差异大时评估 GraphQL |
| 异步任务 | 先用 PostgreSQL 队列或简单 worker | 任务吞吐、延迟、重试拓扑成为瓶颈时再引入专用队列或工作流系统 |
| 缓存 | 先使用数据库索引和 HTTP 缓存 | 有可证明的热点读取或跨实例限流/锁需求时加入 Redis |
| 文件 | 本地开发目录；生产对象存储接口 | 没有文件需求时不引入对象存储 SDK |
| 日志 | `log/slog`，请求 ID，脱敏字段 | 指标和链路追踪在出现真实观测需求时接入，不先堆平台 |

## 架构形态

### 模块化单体优先

默认目录使用一个后端进程和明确模块边界：

```text
HTTP / Controller -> Application Service -> Repository -> Database
                                  \-> Gateway / external client
```

只有同时满足以下条件，才推荐微服务：至少两个团队需要独立发布、模块有独立扩缩容或故障隔离需求、部署和观测能力已经准备好。否则记录为延期，而不是建立空的服务目录。

### 前端渲染选择

- 纯后台、控制台、登录后产品：Vue + Vite SPA。
- 首页、内容页、商品页需要搜索引擎抓取：Nuxt 或独立的静态/SSR 站点。
- 产品和官网同时存在：默认拆成两个前端入口，避免让后台产品承担 SEO 复杂度。

### 数据访问选择

- 业务以标准增删改查、关联预加载和事务为主：GORM。
- 关键读路径包含复杂 SQL、报表、窗口函数或需要严格查询审查：sqlc/原生 SQL，只在热点边界使用，不迁移所有 CRUD。
- 金额、额度、库存和幂等：数据库约束 + 明确事务边界优先，缓存不能承担最终一致性。

## 必须输出的反向建议

每次决策至少明确三项当前不引入的组件，并写出触发条件：

- 没有命中和失效证据时不加 Redis。
- 没有跨团队独立发布需求时不拆微服务。
- 没有事件流和吞吐证据时不加 Kafka。
- 没有 SSR/SEO 需求时不把 Vue SPA 换成 Nuxt。
- 没有查询瓶颈时不把 GORM 全部替换为 sqlc。

## 验收指标

如果是概念验证，写出退出条件，例如首个闭环可重复运行、关键错误可观察、数据可回滚。

如果是生产项目，至少给出三个数字：

- API：p95 或 p99 延迟目标。
- 前端：移动网络下 LCP/INP/CLS 或等价目标。
- 服务：可用性、任务成功率或数据丢失上限。

指标未知时输出建议值并标注“待确认”，不能把建议值伪装成用户承诺。
