# Mapcode

生成跨 AI 共用的业务地图，不是仅记录路由或目录。默认事实源为 `docs/ai/BUSINESS_MAP.md`；它必须同时回答：业务为什么发生、数据和状态如何改变、规则在哪里执行、失败如何收敛、修改时应动哪里以及如何验证。

详细输出结构见 [业务地图模板](references/business-map-template.md)。

## 不可省略的原则

1. **任务优先**：开发者和 AI 按“要改什么业务”检索。每个任务必须列出代码落点、前置条件、陷阱、受影响业务链和验证方式。
2. **业务与实现分层**：业务链不是 `Controller -> Service -> Repository`。同时记录业务流、显式控制流、数据与状态流，三者互相校验。
3. **符号优先**：只保存 `文件路径 -> 函数/类型/SQL/配置键`，不保存行号。跳转时运行 `scripts/where.sh <文件> <符号>` 获取当前行号。
4. **证据优先**：没有找到显式调用、状态写入或事件生产/消费时，不得猜测；标记未确认、验证路径和盲区。
5. **唯一事实源**：完整业务结论只能维护在业务地图。AI 规则文件只引用它，禁止复制正文形成多份漂移版本。

## 上下文路由协议

将业务地图组织为可按需加载的三层上下文，而不是要求每个新任务通读全部文档：

- **L0 - AI 入口**：`AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 或 Cursor 规则仅引用 L1。
- **L1 - 任务路由索引**：`docs/ai/BUSINESS_MAP.md`。保持在 160 行以内，必须包含“任务路由索引”、业务域摘要、全局不变量和跨域依赖。
- **L2 - 领域上下文包**：`docs/ai/business/<领域>.md`。包含该领域完整业务链、三种关系图、任务改动点、前置条件、陷阱、补偿和证据。

每个 L1 路由条目必须给出：用户会说的任务/关键词、最小读取集、可选扩展包、首个代码锚点、受影响状态或不变量、验证项。不要只用目录名或“支付模块”一类宽泛描述。

新任务必须遵循以下协议：

1. 读取适用的 L0 入口和 L1 任务路由索引。
2. 根据用户任务的动词、领域词和实体匹配路由条目，只读取列出的 L2 包。
3. 若条目标记跨域依赖，再读取其依赖包；随后用代码锚点定位源码。
4. 若没有匹配项，先搜索 L1/L2 的标题和关键词；仍找不到时再探索源码，并在完成后补充路由条目和领域包。
5. 不得在新任务中凭旧会话记忆跳过 L1。L1 的“最后核对”和代码证据优先于会话记忆。

## 项目约束与 AI 同步

1. 从项目根目录到当前目录读取全部适用的 `AGENTS.md`，按层级遵循其文档位置、语言、格式和编辑边界。若项目已有业务文档位置，以项目规定替代默认路径。
2. 搜索已有 AI 入口：`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.cursor/rules/*.mdc`、`.cursorrules`、`.windsurfrules`。
3. 对已存在且无冲突的入口，只追加一条引用；不覆盖、不重排既有内容。引用必须要求先读 L1 再按路由加载 L2。仅当用户明确要求接入尚未配置的 AI 时，才创建其入口文件。
4. Cursor 规则遵循项目现有 frontmatter；没有既有规则时可用 `alwaysApply: true`。任何入口均不可复制业务地图正文。

引用使用项目实际路径，默认表达为：

```markdown
在业务理解、方案设计、代码修改、评审或排障前，先读取 `docs/ai/BUSINESS_MAP.md` 及当前领域的明细文件；业务结论只在这些文件中维护。
```

## 建图流程

### 1. 发现业务域和核心链

从产品文档、接口和命令入口、路由、事件、状态表、消息队列、定时任务、权限、计费、库存和外部回调中归纳业务域。先识别改变用户权益、资金、订单、库存、权限、风控结果或对外状态的 3 至 8 条链。

对每个业务域记录不超过三行的职责、关键入口、关键实体和拥有该规则的代码模块。不要罗列所有目录或普通 CRUD。

运行 `scripts/count_sources.sh <项目根目录>` 获得规模提示。源文件不超过 50 个且核心链不超过 4 条时可用单文件；否则使用总览加 `docs/ai/business/<领域>.md` 明细。复杂度来自业务链和状态，不只来自文件数量。即使单文件，也必须保留任务路由索引。

### 2. 建立业务链档案

每条核心业务链必须记录下列信息。缺失时写“未确认”，附源码、测试、日志或负责人等验证路径。

1. **业务契约**：目标、发起角色、受益者、触发方式、输入、输出和成功定义。
2. **状态与数据真相**：实体、状态机、状态写入位置、读模型、幂等键、事务或并发控制；写明关键字段从何处来、如何转换、最终写到哪里。
3. **主业务流**：入口、校验、关键分支、状态迁移、异步分支和最终业务结果。
4. **关键规则与不变量**：权限、定价、额度、库存、风控、状态前置条件、数据边界和不可被绕过的规则；说明违反后果。
5. **副作用与恢复**：写库、扣费、发消息、第三方调用、通知、缓存；分别说明顺序、重试、幂等、超时、补偿、退款/回滚和人工兜底。
6. **实现证据**：每个关键业务步骤的 `路径 -> 符号`、SQL、事件主题、配置键或外部协议；只引用已验证的关系。
7. **验证与观测**：相关测试、审计/埋点/日志、监控指标和告警；明确尚未覆盖的故障模式。

### 3. 为每条链绘制三种关系

- **业务流图**：参与者、业务状态、规则、外部系统、失败和最终价值结果。它应让不了解代码的人看懂业务走向。
- **控制流图**：只画源码中可确认的显式函数调用、分支分发、接口实现、消息生产和消费。隐式 ORM 钩子、反射、自动注册或事件订阅不许臆测，改写为“未追踪”。
- **数据与状态流图**：输入字段或事件载荷如何解析、校验、转换、持久化、异步传递和对外输出；关键状态写入必须标出存储或事件。

用 Mermaid `subgraph` 明确异步或并行分支。每张图通常不超过 12 个节点；线性管线或同一决策树无法安全拆分时可保留到约 18 节点，但须添加：

```markdown
<!-- no-split: 同一状态机的分支共享前置状态；拆分会丢失状态迁移关系 -->
```

每张图都要追加证据与盲区：

```markdown
<!-- confidence: high - 已核对显式调用、关键状态写入和对应测试 -->
<!-- evidence: payment/service.go -> ConfirmPayment；payment_records.status；TestConfirmPayment -->
<!-- blind-spots: 第三方回调的最大重试次数尚未确认 -->
```

`high` 必须实际抽查；仅凭命名或运行习惯推断的结论最高是 `medium`，并给出可执行验证命令或位置。

### 4. 维护任务索引

业务地图总览必须按真实开发动作建立任务路由索引。每项包含：

1. 受影响的业务链和领域。
2. 需修改的文件和符号，按执行顺序列出。
3. 前置条件、关键规则和容易遗漏的边界。
4. 必须验证的状态、金额/权限/库存影响、测试和观测信号。
5. 最小读取集和跨域时需要追加读取的上下文包。

任务索引不能只写“改接口”或“改服务”。例如支付回调改动必须指出幂等键、订单状态、扣费/发货顺序、重复回调补偿和对应测试。

### 5. 增量更新与规模治理

更新前读取已有总览、领域明细和最后一条变更摘要；只记录业务事实差异，不记录“分析了某函数”。先备份将被改写的地图文件为同名 `.bak`。

以下人工知识必须逐字保留：

```markdown
<!-- manual: keep -->
人工确认的事故结论、业务陷阱、前置条件和不变量
<!-- /manual -->
```

- 总览保留业务域表、任务索引、跨域依赖、全局不变量和变更摘要；详细三图和业务链档案放在领域明细。
- 运行 `scripts/check_size.sh docs/ai 240`。超过阈值时按业务域拆分，不删除任务索引、不变量或人工保护块。
- 运行 `scripts/check_context_links.sh docs/ai/BUSINESS_MAP.md`，确认路由索引指向的领域包真实存在；缺失链接不能标记为完成。
- 每个变更日志最多 20 条，最旧记录折叠进摘要；人工保护的里程碑不裁剪。
- 删除文件或符号时清理失效任务索引；每次用 `scripts/where.sh` 复核保留的代码锚点。

## 完成条件

1. 每条核心链至少验证一个关键决策和一个状态写入；金额、权限、库存、额度、状态机链还必须记录幂等与失败补偿。
2. 每个任务索引符号都存在，且前置条件、陷阱、受影响链和验证方法齐全。
3. 高置信度图都有实际证据；未追踪的运行时行为、缺少测试和外部系统假设都显式列在盲区。
4. 已接入的 AI 入口只引用事实源，所有业务正文只保留一份。
5. 用一个不依赖当前会话的新任务描述模拟路由：从 L1 找到对应 L2、代码锚点和验证项；无法在两步内定位时，补充任务关键词或拆细路由条目。

交付时报告业务域数量、核心链数量、任务索引数量、已接入 AI、已验证证据和仍需人工确认的业务风险。不要以“文档已生成”替代这些结论。
