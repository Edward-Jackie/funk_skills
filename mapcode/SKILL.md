# Mapcode

Mapcode 保存 Agent 难以从局部源码快速恢复的业务语义，并把业务规则与当前实现的冲突显式暴露出来。它不是源码副本，也不自动成为所有内容的“唯一事实源”。

详细字段与示例见 [证据与新鲜度规范](references/evidence-model.md) 和 [业务地图模板](references/business-map-template.md)。创建或大规模改造地图时读取模板；日常维护只需读取证据规范。

## 权威边界

地图必须区分两类内容：

- **规范性事实**：负责人确认的业务不变量、事故结论、合规或运营约束。只有标记为 `human-confirmed` 的内容可作为业务要求引用。
- **描述性事实**：从源码、测试或运行环境核对出的当前实现。源码决定当前实现，数据库和运行验证决定实际状态；地图只是带证据的快照。

业务要求与实现不一致时，不得替任一方圆场。用 `conflict` 同时记录规则、实现、风险和待决策项。

## 应该记录什么

优先记录改变用户权益、资金、订单、库存、权限、额度、风控结果或对外状态的核心链：

- 业务目标、发起角色、成功定义和边界。
- 状态真相、关键字段来源、事务、并发控制和幂等键。
- 不可被绕过的规则及违反后果。
- 跨存储或第三方副作用的顺序、重试、补偿和人工兜底。
- 实现证据、验证方式、观测信号、盲区和已知冲突。
- 真实开发任务对应的最小读取集、首个锚点和影响面。

不要记录 Agent 现场搜索更可靠的内容：普通目录树、机械的 Controller 到 Service 罗列、无状态 CRUD、完整接口清单和重复的项目规范。

## 文件命名与扁平结构

所有项目统一使用以下结构，不接受项目自定义路径、别名或子目录：

```text
.codex/
├── MAPCODE.md
├── MAPCODE-<领域>.md
└── MAPCODE-<另一领域>.md
```

- L0：根目录 `AGENTS.md` 等 AI 入口只引用 `.codex/MAPCODE.md`。
- L1：必须且只能命名为 `.codex/MAPCODE.md`，保存任务路由、业务域摘要、全局不变量和冲突摘要；建议不超过 120 行，硬上限 160 行。
- L2：必须与 L1 同目录，命名为 `.codex/MAPCODE-<领域>.md`；`<领域>` 使用小写英文、数字和连字符，例如 `MAPCODE-billing.md`、`MAPCODE-agent-routing.md`。
- 禁止使用 `BUSINESS_MAP.md`、`docs/ai/`、`.codex/business/`、嵌套领域目录或其他前缀。禁止只改链接而保留错误路径的旧地图。
- 小型项目不需要拆 L2 时，只保留 `.codex/MAPCODE.md`；需要拆分时仍必须保持扁平结构。

## 上下文路由

处理新任务时：

1. 读取 L1，按任务动词、实体和故障现象选择最小 L2。
2. 先检查领域包的 `status`、`verified-commit` 和冲突；`stale`、`needs-review` 或 `conflict` 不得直接作为实现事实。
3. 从锚点进入源码，核对本次任务实际依赖的决策、状态写入和失败路径。
4. 找不到路由时再探索源码，完成后只补充可复用的业务知识。

每个 L1 路由条目应包含任务关键词、最小读取集、可选扩展包、首个代码锚点、关键规则和验证项。小型局部改动不必强制加载无关领域包。

## 证据分级

关键结论使用下列标签，不再使用笼统的 `high confidence`：

- `human-confirmed`：人工明确确认的业务要求。
- `source-verified`：已核对显式调用、分支或状态写入。
- `test-verified`：相关自动化测试已通过并覆盖该结论。
- `runtime-verified`：已在真实依赖或目标环境验证。
- `unverified`：尚未取得足够证据。
- `conflict`：规范、源码、测试、数据库或运行结果互相矛盾。

标签必须附证据。运行验证不能由源码阅读代替，测试存在也不能自动推断测试覆盖了该结论。

## 建图与更新

先识别 3 至 8 条高风险核心链，再按需拆领域包。业务流、控制流、数据状态流只有在能显著降低理解成本时才绘制，不强制每条链固定三张图。

代码锚点使用 `文件路径 -> 符号/SQL/配置键`，不保存行号。没有找到显式证据时标记 `unverified`，并给出验证路径，不得凭命名补全调用关系。

增量更新时：

1. 读取 L1、目标 L2、其元数据和最后一条变更摘要。
2. 对照当前源码或运行证据，只修改发生变化的业务事实。
3. 规则与实现冲突时新增冲突记录，不得静默改写人工规则。
4. 更新 `verified-at`、`verified-commit`、`status` 和证据标签。
5. 地图应进入版本控制，与对应业务代码一起评审和回滚。

人工确认内容继续使用保护块：

```markdown
<!-- manual: keep -->
[RULE][human-confirmed] 人工确认的不变量、事故结论或业务边界。
<!-- /manual -->
```

## 校验

在项目根目录运行：

```bash
scripts/check_map.sh .codex/MAPCODE.md
scripts/check_map.sh --strict .codex/MAPCODE.md
```

普通模式报告缺失链接、失效锚点、过期领域包和冲突；严格模式将 `needs-review`、`stale`、`conflict` 作为失败，适合 CI。首次迁移旧地图时允许标记 `needs-review`，不得为了通过检查伪造已验证状态。

`scripts/where.sh <文件> <符号>` 用于取得当前行号。`scripts/check_map.sh` 必须拒绝错误的 L1 文件名、嵌套 L2 和不符合 `MAPCODE-<小写领域>.md` 的领域包。

## 完成条件

- L1 能在两步内把真实任务路由到最小领域包和首个代码锚点。
- 金额、权限、库存、额度和状态机链记录不变量、幂等及失败补偿。
- 每条关键结论都有准确的证据标签；运行盲区没有被标成运行验证。
- 业务规则与实现差异已进入冲突清单。
- 链接、锚点和新鲜度检查通过，或未通过项被明确交付为待处理风险。
- 地图已纳入版本控制；未纳入时必须将整体状态标为 `needs-review`。
