# Weekly Summary — 周报生成

提取用户本周的开发工作，生成周报。**核心原则：把所有"让模型自由判断"的点都收敛成硬规则 + 真实样本 + 显式询问，不给模型飘的空间。**

## 第 0 步：强制询问模式（不可跳过）

触发本 skill 时，**必须先用 AskUserQuestion 工具问用户**要哪种模式，不要自己猜。选项固定为：

1. **模式 A**：详细周报（默认，给团队看/发邮件/存档）
2. **模式 B**：精简清单（只列模块名，快速回顾）
3. **模式 C**：自定义（用户提供示例格式，严格照抄）
4. **模式 D**：复用上次（沿用上次的模式，本次不切换）

**只有当用户在触发词里就明说了模式**（如"简单点列个清单"→B、"参考上次那种"→C），才可跳过询问直接用对应模式。**其他情况一律问，禁止自己猜。**

## 数据来源（两者结合，互相补充）

1. **当前会话历史**：用户在对话中提出的开发需求、讨论过的方案。
2. **git 提交记录**：会话历史覆盖不到本周全部工作时，用 `git log --since="7 days ago" --pretty=format:'%ad|%s' --date=short` 补齐，按需 `git diff`/`git show` 理解某条 commit 的实际内容。
3. 两者冲突或重复时，**以 git log 为准**（口头讨论不一定落地）。

## 粒度硬规则（消除"明显不同"的模糊判断）

**一条周报条目 = 满足以下任一条件：**
- 一个独立 PR / 一个独立 merge
- 一个独立功能特性（跨多个 PR 也合并为一条）
- 一个独立 bug 修复（同 PR 内的多个相关修复合并为一条）

**必须合并为一条：**
- 同一 PR 内的多次微调（如"调样式"、"改文案"、"补注释"）
- 跨 PR 但属于同一功能的不同阶段

**必须拆开：**
- 不同子系统 / 不同模块的改动
- 同一模块下功能上不相关的两个改动（如"计费修复"和"计费配置项新增"是两件事，不能合成一条）

## 输出原则（不因格式改变）

1. **突出功能价值**：写"实现了什么能力"、"解决了什么问题"，不写"改了哪些文件"
2. **业务成果导向**：强调对业务的影响
3. **去技术细节**：不写文件名、行号、函数名、变量名、类名
4. **按功能模块分组**：同模块多次相关提交合并

## 模式 A：详细周报（默认）

面向汇报/存档。**结构硬约束：3-5 个模块，每模块 2-3 句**（不用字数约束，模型数不准；用结构化数量约束）。

✅ 正确样例（真实样本风格，照这个模仿）：

```markdown
# 周报

## 1. 计费系统
- 完成跟价封顶逻辑，避免大额订单超额计费
- 修复专属价与普通价混用时的隔离问题，保障计费准确性
- 业务影响：规避潜在资金风险

## 2. 用户中心
- 上线手机号换绑流程，支持验证码二次校验
- 解决旧账号绑定关系迁移的历史遗留问题

## 3. 配套工作
- 补充计费模块设计文档
- 修复周报生成 skill 的格式飘移问题
```

❌ 反例（**不要**这样写）：

```markdown
# 周报
本周改了 billing/cap.go、user/phone.go、doc/billing.md 三个文件，
主要是在 cap.go 里加了 maxPrice 字段，phone.go 里加了 SendCode 函数...
```

> 反例错在哪：暴露文件名/函数名、逐条罗列 commit、没按模块分组、没业务价值、用"改了 XX 文件"的口径。

## 模式 B：精简清单

只列模块名，不展开描述。**结构硬约束：平铺编号（1./2./3.…），不带顶层模块标题，每条一行，每条不超过 15 字，粒度比 A 更细**（同大模块下不相关子任务必须拆开，但不再加模块分组标题，直接连编号平铺）。

✅ 正确样例（用户 aiProxy 项目真实周报，照此风格模仿——平铺编号、无顶层标题、动作词收尾）：

```
1. 登陆、注册页面优化
2. 前端组建重构
3. 企业用户实名限制
4. 订单统计逻辑修复
5. 账单任务健康探针
6. 企业用户页面白名单逻辑优化
7. 跨域配置增加映射
8. 前端页面指标统一
```

❌ 反例（**不要**这样写）：

```
- 计费：做了跟价封顶和专属价隔离两件事，还修了一些 bug
- 用户中心：上线了手机号换绑功能，解决了历史遗留问题
```

> 反例错在哪：合并了应该拆开的条目（A 模式才合并，B 模式必须拆细）、加了描述（B 模式不准带描述）、用破折号不用编号、超 15 字。

## 模式 C：自定义（照抄用户示例）

用户给示例时，**逐项对齐这 5 个维度，不要自作主张改动**：

1. 是否有顶层项目名/标题
2. 编号风格（`1.` / `-` / 纯换行）
3. 每条是否带子说明，子说明是几行
4. 模块粒度（粗=按系统分，细=按具体改动分）
5. 语言风格（带业务价值解释 vs 纯动作描述）

生成后只说一句"已按你给的格式改造"，不必逐项列对比。

## 模式 D：复用上次

用户没明说模式，且历史记录里有上次的周报模式时，直接用上次的，并在开头说一句"沿用上次 X 模式，如需切换告诉我"。**不要在 D 模式下自创格式。**

## 流程

0. **强制询问模式**（除非用户已明说）—— 必须用 AskUserQuestion 工具
1. 收集本周工作：先看会话历史，再用 git log 补齐/核对
2. 按"粒度硬规则"归类合并
3. 按选定模式排版
4. **输出前自检**（见下，过一遍再吐）
5. 输出到用户指定路径；未指定且不长时直接对话给出；用户要求保存或内容长时写文件（默认 `/Users/jack/dev/temp/weekly_summary.md`）

## 输出前自检清单（产出后过一遍再吐）

- [ ] 模式对不对（A/B/C/D 是否符合用户选的，没有自创第五种）
- [ ] 粒度对不对（按"粒度硬规则"判定，该合的合该拆的拆）
- [ ] 有没有泄露文件名/函数名/变量名/类名/行号
- [ ] 有没有逐条罗列 commit（应该按模块分组）
- [ ] 结构硬约束是否满足（A: 3-5 模块每模块 2-3 句；B: 每条一行≤15字；C: 5 维度全对齐；D: 完全等同上次）
- [ ] 有没有混用多种模式的特征（如 B 模式里冒出描述句）

**任何一项不过，重写对应部分再吐，不准将就着吐出来。**
